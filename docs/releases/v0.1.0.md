# MCP ToolHub v0.1.0

MCP ToolHub is a local, stdio-only MCP execution gateway that gives an AI
agent a deliberately bounded workspace and Git surface while keeping human
approval outside the MCP trust boundary.

Its three central differentiators are:

- Human-only decisions through the separate `mcp-toolhub-admin` CLI; there is
  no MCP approval or rejection tool.
- Immutable, expiring approval snapshots that are consumed atomically and at
  most once before an approved mutation or external command runs.
- Confined workspace access, guarded Git inspection, process-tree lifetime
  containment, bounded output, and a sanitized bounded audit trail.

## Installation

Download all three release assets, verify both package checksums, then install
the wheel with [uv]:

```text
sha256sum --check SHA256SUMS.txt
uv tool install ./mcp_toolhub-0.1.0-py3-none-any.whl
mcp-toolhub --version
```

The final command must report `0.1.0`. Source installation and Windows
PowerShell setup are covered in the [operations guide].

## Compatibility and protocol

- Supported operating systems: Ubuntu/Linux and Windows.
- Validated interpreters: Python 3.12 and Python 3.13.
- Required interpreter: Python 3.12 or newer.
- Package version: `0.1.0`.
- Protocol contract: Contract V1, version `1.0`.
- Production MCP inventory: exactly 14 tools.

Package releases and the Contract V1 protocol are versioned independently.
The Contract V1 schemas, annotations, operation mappings, outcomes, and
approval lifecycle are locked by a source-controlled compatibility fixture and
tests.

## Security model

Workspace paths are canonically confined, and mutation paths reject traversal
and symlink escapes. File changes and external commands use protected approval
snapshots in trusted state outside the workspace. Approvals expire, bind to one
workspace and executable identity where applicable, and are consumed before
execution. Command and fixed Git-helper execution use OS-backed process-tree
lifetime containment with bounded runtime and output. State and audit writes
are locked, hardened, and atomically published.

These controls reduce confused-deputy and replay risk; they do not make an
approved program safe or sandbox its filesystem or network access.

## Limitations and non-goals

- Local stdio operation only; no HTTP, SSE, cloud, or remote gateway.
- Single-user trust model; no authentication, RBAC, or multi-user service.
- No autonomous or agent-driven approval.
- No general filesystem, network, CPU, memory, container, or kernel sandbox.
- Audit records are intentionally bounded and sanitized rather than a capture
  of raw command output.

See the [README], [architecture and threat model], [approval lifecycle],
[demo], and [operations guide] for details.
